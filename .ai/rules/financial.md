# Financial

## Lot tracking: explicit financial_lots rows, soft negative-lot validation
Lots are explicit rows (financial_lots: financial_commodity_id, acquired_at date, cost = TOTAL acquisition cost in USD as an exact decimal, metadata), never derived with booking algorithms. Postings carry a nullable financial_lot_id: one posting touches at most one lot — a multi-lot sale is one reduction posting per lot. Lot quantity and location are DERIVED: SUM(amount) of referencing postings, per account. acquired_at defaults to the transaction date but is editable (in-kind transfers carry older basis).
Negative-lot states are SOFT: never block saves that drive a lot negative (backdating, edits, oversell) — a derived checker walks the lot's postings in (date, transaction id, position) order and flags the first posting taking the running sum below zero. Hard validation is structural only: lot commodity must equal posting commodity. Partial consumption allocates basis pro-rata under the fixed-decimal rule below.

## Journal design: balance at cost, posting-level status, derived transaction state
Transactions balance AT COST (no equity:conversion ceremony): value lot-bearing legs at allocated lot basis, USD legs at face — must sum to zero. Sales therefore carry an explicit income:capital-gains posting; realized gains are journal data, never derived at report time. Balance is HARD-validated at save; a lot edit that retroactively unbalances an old transaction becomes a soft checker issue (same mechanism as negative lots), never a blocked save.
Status lives on postings only (Pending/Cleared/Reconciled) — reconciliation is per account. Transaction status is DERIVED from its Asset/Liability postings (aggregation rule settled at implementation). No drafts, no voids: deletes are guarded instead. Posting order within a transaction is an explicit position column, unique per transaction.

## Fixed 25-place decimal storage
Posting amounts, lot costs, and commodity prices use NUMERIC(78,25) and Brick Math BigDecimal: 53 integer digits and 25 fractional digits. Assign them from strings, integers, or BigDecimal values — never floats. API values are unscaled decimal strings; reject overflow/excess fractional digits rather than silently rounding. Commodity display_precision (0–25) controls formatting only and can change without rescaling data. Lot costs remain total USD costs. Basis allocation floors at 25 fractional places and distributes the combined-target shortfall by descending remainder, ties by posting order.

## Recurring transactions: schedules materialize real transactions within a lead window
Scheduled/recurring entries are NEVER drafts. A schedule (financial_recurring_transactions, model RecurringTransaction) holds payee, memo, posting templates (financial_recurring_postings, each with its own status so accruals can be born Cleared while bank transfers are born Pending), frequency (RecurrenceFrequency: daily/weekly/monthly/yearly) x integer interval (biweekly = weekly/2, quarterly = monthly/3), starts_on (anchor), next_due_on (pointer), optional ends_on. Occurrences are computed from the anchor, not the previous occurrence, with Carbon *NoOverflow clamping so a 31st schedule never drifts. No RRULE package. Instances are ordinary transactions dated on their due date, written through TransactionWriter, with a nullable financial_recurring_transaction_id (nullOnDelete) that API edits never clear.
Materialization policy: "anything due within N days" where N is the schedule's nullable lead_days, else config('financial.recurring_lead_days') (day-of is 0). RecurringTransactionMaterializer loops: while next_due_on <= today + N (and <= ends_on), write an instance dated next_due_on and advance the pointer. It runs from `financial:post-recurring` (daily 05:30 Eastern, after the 05:00 price fetch) AND immediately on schedule create/update (RecurringTransactionWriter), so a past start date backfills. Deleting an instance never rewinds the pointer (that is how "skip" works). Editing a schedule replaces its templates and never rewrites posted instances; the form's date is "when the next one is due" — a changed date re-anchors (starts_on = next_due_on = date), an unchanged date keeps the anchor.
Entry point is the journal: TransactionForm gains a Repeat section; empty = POST transactions, filled = POST/PUT recurring-transactions with the same posting payload (StoreRecurringTransactionRequest extends StoreTransactionRequest: lot rules swapped for a base-currency-only check). "Duplicate" is the same form pre-filled with ids stripped and the date reset to today. Before saving, the form shows exactly the dates a save will post, from POST recurring-transactions/preview/{schedule?} (occurrence math lives only in PHP). /finances/schedules lists and edits schedules; creating there is secondary. Currency-only postings; lot-bearing legs are out of scope.

## Bank transactions are staged evidence linked per posting, managed from the account page
financial_bank_transactions holds bank-reported rows (SimpleFIN today; source + external_id unique so other sources can share it). Importing NEVER writes to the journal: a row joins the ledger only when financial_posting_id is set. The link is on the POSTING, not the transaction, so a transfer between two mapped accounts is one transaction with two bank rows each settling their own leg; deleting a linked posting nulls the link (nullOnDelete). Unmatched = null link. Rows are worked from the account page (band above the register, Approve on an exact-match register line, hand match, convert to a new transaction) — there is deliberately no global inbox (the 2026-09-11 inbox attempt was reverted for lacking register context). Pending rows are captured and shown; the importer upserts by external id so a pending row settles in place.
Sync is per account: POST financial/accounts/{account}/simplefin-sync (SimpleFinImporter::sync) asks the bridge for that one account (account= query param), pending=1, from initial_days back on the first sync, else overlap_days before the account's newest row. Bank timestamps become calendar dates in config('financial.simplefin.timezone'). Every sync stores simplefin_synced_at / simplefin_balance / simplefin_balance_date on the account for the header. No scheduled sync yet — manual from the header by design.
